## 2 项目结构与职责

```text
xiaozhi-agent-training/
├── 项目总文档.md                 进度、流程和后续事项
├── README.md                    简短入口与运行命令
├── config.json                  模型、来源及独立评估种子规模
├── system-prompt.txt            统一行为规则
├── data/
│   ├── raw/                     原始轨迹和最新修订评分
│   └── prepared/                SFT 训练集、未通过、待复核、盘点与报告
├── scripts/                     数据准备、评估种子生成；后续加入训练和模型评测

├── tests/                       程序自检和整批数据验收

```

本项目负责保存提示词、盘点与筛选源数据、生成训练数据集、准备评估种子，以及后续训练和模型评测。真实家居服务、在线 agent 服务和源对话生成继续由各自流程负责。

评分器复用 server 的相同逻辑，在本项目内保存独立版本，不另写一套判断标准。数据准备脚本读取已有评分并检查样本对应关系、检查项及证据；这不等于重新调用模型评分。训练后模型运行入口、工具环境适配和语义评分调用入口尚未实现。

## 4 已落实：源数据盘点与训练集生成

本阶段由一个导出脚本完成：读取源数据 → 盘点 → 整理模型输入 → 检查与分类 → 去重 → 输出 SFT 训练数据集。

### 4.1 来源与评分

| 场景 | 原始轨迹 | 最新评分通过 | 最新评分未通过 |
|---|---:|---:|---:|
| 天气 | 300 | 283 | 17 |
| 家居开关 | 299 | 288 | 11 |
| 合计 | 599 | 571 | 28 |

原始文件保存在 `data/raw/weather/` 与 `data/raw/home_switch/`，分别包含 conversations.json 和 scores.current.json。均采用已修订的最新评分，不再比较旧规则。原始轨迹和评分文件保持不变。

### 4.2 程序盘点只统计三项

| 维度 | 统计内容 |
|---|---|
| 来源与数量 | 每个来源文件作为一批，记录场景、数量和原有 run_id |
| 任务覆盖 | template_id、variable_group_id、question_pattern_id、variant_id、scenario_ids 的已有取值及样本数 |
| 对话结构 | 单轮、多轮数量，以及消息数、正文字符数、工具调用次数、单次调用参数字符数的分布 |

盘点面向全部 599 条轨迹，包括未通过、待复核和重复项。任务标签直接读取 seed，缺失记录为“未提供”，不推断新标签。一个样本可包含多个场景标签，因此标签数量不能相加作为总样本数。

轮数按真实 user 消息计算，排除 internal_message_indices 标记的运行器提示。消息数和正文字符数统计原始完整轨迹，包含 system 和运行器消息；正文不包含工具调用参数。参数字符串按原文计数，对象按紧凑 JSON 计数。这些都是字符数，不是模型 token 数。

分布提供最小值、中位数、P90 和最大值；P90 使用最近秩法，即升序第 ceil(0.9×数量) 项。无观测值时统计值为 null，不伪装成零。

当前天气有 165 条单轮、135 条两轮；家居有 87 条单轮、197 条两轮、15 条三轮。具体模板、变量组和标签计数见 `inventory.json`，摘要见 `report.md`。本流程不生成覆盖不足分析或补数建议。

### 4.3 每条训练输入如何构成

| 部分 | 做法 |
|---|---|
| system 固定规则 | 使用根目录 system-prompt.txt，涵盖共同规则、天气规则和家居规则 |
| system 设备目录 | 从该条原始 system 提取并原文保留可见目录块，包括字段、设备及别名顺序 |
| messages 后续消息 | 保留用户消息、助手回复及调用、工具返回，不改正文 |
| tools | 每条样本携带自身的完整可用工具定义，与 messages 并列 |

天气样本使用 get_weather；家居样本使用原轨迹保存的 state_hub_snapshot 和 hass_set_state。未调用的可用工具也保留，不根据实际调用记录缩小工具集合，不给单场景样本额外添加其他场景工具。

天气旧轨迹没有工具快照，因此使用 `evaluation/weather-tool.json` 中恢复的定义，说明与最新规则一致。它不是历史快照；来源、定义校验值和逐条工具来源均有记录。

日期、时区不从 context 元数据添加。原始用户消息、助手回复和工具返回中的日期正常保留。设备目录必须来自原始 system，并与元数据 public_catalog 对照；不一致或无法可靠提取则进入待复核。目录只提供身份与权限，不能代替工具返回的实时状态。

种子目标、评分答案、模拟器隐藏状态和未来故障计划都不进入训练输入。工具参数从 JSON 字符串转换为对象，随机调用 ID 按顺序规范化，并同步更新对应工具返回的 ID；这些处理不改变调用语义。

### 4.4 检查、分类与去重

导出器检查对话是否完整、消息顺序、工具调用与返回对应关系、参数格式、system 校验值、设备目录，以及评分对应关系、检查项和证据。

| 去向 | 天气 | 家居 | 合计 |
|---|---:|---:|---:|
| SFT 训练数据集 | 283 | 273 | 556 |
| 未通过样本 | 17 | 11 | 28 |
| 待复核 | 0 | 15 | 15 |
| 完全重复项 | 0 | 0 | 0 |
| 总数 | 300 | 299 | 599 |

训练集只接收评分通过且结构与输入检查通过的轨迹。完全相同的规范化 messages 和 tools 才算重复；只保留一条，并记录其他原始样本对应的保留项，不做语义近似去重。

未通过样本保留失败项、证据和错误调用，不自动修成正确答案；对格式可解析的错误工具名或参数，记录 invalid_actions，不为虚构工具补定义。结构本身无法可靠还原的样本进入待复核。

15 条待复核轨迹包含运行器插入的工具调用限次提示。删掉这条提示会改变后续回答的输入条件，因此本次整段保留在 raw，记录来源和原因，不直接用于训练。待复核不代表永久丢弃。

## 5 运行与复现

只需 Python 3.10+ 标准库，无需连接模型、真实设备或原 server。

```bash
python3 -B -m unittest discover -s tests -p 'test_*.py'
python3 -B scripts/prepare_training_data.py --config config.json --output-dir data/prepared-next
```

输出目录必须不存在，脚本拒绝覆盖旧数据。验证新版本后再归档旧版本并切换。配置中的路径相对 config.json 解析，产物清单使用配置路径，整个项目可复制到训练服务器。

评估种子生成器已有独立入口 `scripts/generate_evaluation_seeds.py`，其使用说明见 `evaluation/seed_generation/README.md`。原本借用的 test_fraction 已改名为 evaluation_seed_fraction，保留 0.2 的评估种子规模，不再承担源数据划分功能。本轮未运行种子生成器或变更其生成逻辑。当前生成器仍读取源轨迹和评分，本次未增加对 inventory.json 的自动消费。

## 6 下一阶段：验证 Qwen3.5-9B 训练适配

**直接使用现有 train.jsonl，不重新开展数据准备。** 先锁定准确的模型仓库、revision、tokenizer、思考模式和训练依赖，不能套用早期 Qwen3-8B 的配置。

训练适配需验证三件事：

1. 将每条 messages 和对应 tools 一起交给目标聊天模板。检查工具定义确实进入模型输入，调用与返回格式正确，没有丢失多轮工具交互。
2. 检查真正送进训练器的 token labels。只对 assistant 回复和工具调用计算损失，system、工具定义、user 和工具返回仅作为上下文。metadata 中的 assistant 消息位置只是辅助记录，不等于掩码已经实现。
3. 用实际 tokenizer 测 token 长度，再决定上下文长度和 batch。过长样本不能直接截掉后半段工具链；若需要拆分或移出，记录来源及原因并形成新版本。

只有发现具体格式或内容问题才修订训练集。完成标志是模板渲染正确、工具调用可还原、长度有统计、损失标签有验证实例，训练和推理使用一致的格式与思考模式。

## 7 冻结版本与训练服务器试跑

适配通过后固定数据、system、逐条 tools、代码、模型及 tokenizer 版本，并保存校验清单。冻结后不在训练过程中悄悄修改数据；后续修订形成新版本。

在服务器记录操作系统、驱动、CUDA、Python、PyTorch、Unsloth 和实际训练依赖。按用户确认的单卡 32GB 实测显存消耗，不提前承诺上下文长度或 batch。

先用很小一批数据验证加载、loss、保存恢复和推理工具调用，再确定 batch、梯度累积及 LoRA/QLoRA 参数。当前未设定具体训练参数，也没有训练脚本占位文件。

## 8 SFT、模型评测与后续 DPO

正式 SFT 前，在固定的新评估种子上运行原模型作为基线。训练后使用相同提示词、工具条件和评分规则评测 SFT 模型，比较任务完成、工具选择与参数、重复控制、无依据的成功声明及澄清行为。测试种子不进入训练集。

本阶段没有留出验证集，训练脚本不能默认寻找 test.jsonl。后续如需独立验证 loss，应另行确定验证数据来源；不在当前流程中暗自划分。训练 loss 本身也不能替代任务评测。

SFT 交付模型或适配器、配置、训练日志、加载方式和基线对比。之后再根据实际错误展开 DPO 方案，现存 failed.jsonl 不直接等于 DPO 数据集，也不保证每条失败都能作为 rejected。

最后在相同条件下比较原模型、SFT 和 SFT+DPO，交付选定模型、准确底座及 tokenizer、输入约定、训练配置、评测报告和加载示例。接回 agent server 属于后续集成，不在本项目修改原 server 的部署。
