# Qwen3.5 9B 智能助手微调项目总文档

本项目负责评估源数据、划分数据、保存统一提示词、提取训练和测试数据、运行训练脚本，以及评估训练后的模型。使用已有的天气和家居轨迹，在独立训练服务器上完成这些工作。

当前停在数据准备阶段：已经有可重复执行的筛选和导出脚本，尚未适配 Qwen3.5-9B 的训练格式，也没有开始训练。SFT 之后保留 DPO 阶段，但现在不提前做 DPO 数据评估或配对。

这份文档是项目的主入口。已完成的部分写清楚“做了什么、产物在哪里、验证到什么程度”；未来部分写清楚“下一步要做什么、为什么要做、怎样算完成”。后续每次确认和执行都更新这里，不需要在聊天记录中翻找进度。

SFT 可以理解为“给模型看正确示范，学习怎么完成任务”。DPO 可以理解为“在同样的问题和上下文下，告诉模型哪种回答或操作更好”。两者都需要可靠数据，第二阶段不能自动补救第一阶段的数据问题。

## 2 项目只负责这些工作

| 工作 | 输入 | 输出 |
|---|---|---|
| 评估源数据 | 原始轨迹、最新评分 | 通过、未通过、待复核三类结果 |
| 划分数据 | 全部来源样本及分组信息 | 固定的训练侧与测试侧划分 |
| 保存统一提示词 | 已确认的助手行为和工具规则 | 同一份 system 提示词与工具定义 |
| 提取训练和测试数据 | 通过检查的轨迹、划分、提示词 | 模型可使用的训练和测试数据 |
| 训练 | 数据、模型和训练配置 | SFT 模型，后续按阶段开展 DPO |
| 评估模型 | 模型运行得到的新轨迹、统一评分规则 | 原模型与训练后模型的对比报告 |

生成新对话、维护真实家居工具、提供在线 agent 服务，继续由原来的生成与服务端流程负责。本项目接收它们输出的数据；发现覆盖不足时，提出补数要求，再导入补充批次。训练过程不依赖运行中的 server。

目录按上述职责组织，不为每一个说明或计划单独建目录：


日常主要看总文档、配置、提示词和导出报告。`README.md` 只是入口；`tests` 用于程序检查；历史材料集中到 `archive`，不再分散在根目录。整个项目可复制到训练服务器，活动配置均读取项目内文件。

### 评分器怎么处理

**复用 server 的同一套评分逻辑，在本项目内保存可独立运行的版本，不另写一套判断标准，也不跨目录调用运行中的 server。** 现有规则与代码放在 `evaluation`。规则以后有修订时，明确同步版本，并重新评分受影响的数据。

“评分器”和“评测入口”是两件事：评分器判断轨迹对不对；评测入口负责加载某个模型、发送测试任务、运行工具环境、保存新轨迹，然后交给评分器。

| 部分 | 当前情况 | 后续工作 |
|---|---|---|
| 评分规则与程序检查 | 已从 server 复用独立副本 | 沿用最新规则，维护一致性 |
| 读取已有评分、检查对应关系 | 已在数据准备脚本中实现 | 继续用于源数据筛选 |
| 对新轨迹调用语义评分模型 | 本项目尚未接入调用入口 | 复用原评分流程的规则与格式，不重写标准 |
| 加载训练后的模型并跑测试 | 尚未实现 | 在 scripts 中加入模型评测入口及工具环境适配 |

这样可以保证源数据和训练后模型按同一标准检查。当前没有训练脚本或完整的模型评测入口；这些都是后续明确的工作，不是已经完成的能力。

## 4 步骤一 原始数据盘点

### 已经收到什么

|---|---:|---|
| 天气 | 300 | `data/raw/weather/conversations.json` |
| 家居开关 | 299 | `data/raw/home_switch/conversations.json` |
| 合计 | 599 | 两批数据保持各自来源 |

这次实际读到的家居文件是 299 条，不能因为生成计划可能写了 300 就把缺少的一条补成假数据。是否另有未完成或失败的生成任务，后续需要新增数据时再回到生成阶段确认。

轨迹中保留了 system、用户消息、助手回复、助手工具调用和工具返回。家居数据还保存了工具定义、可信设备目录以及用于评分的模拟环境信息。天气旧轨迹没有保存当时的工具定义，因此暂时从现有工具源码恢复定义，并在记录中标为“当前源码恢复”，不假称它就是历史快照。

### 原始数据为什么不直接训练

原始 JSON 里既有模型当时看到的消息，也有评分需要的答案线索。例如种子可能写有最终目标设备，模拟器可能保存尚未发生的故障和环境状态。这些信息适合检查模型是否答对，但不能提前交给模型。

因此训练输入与审计信息必须分开。原始文件完整保留；导出器只选择应该成为输入的部分。迁移没有修改原始轨迹内容，也没有删掉失败案例。

### 本步已落实的检查

两批文件的数量已经核对；每条数据都记录了去向。原始文件和采用的评分文件保存 SHA-256 校验值，可用来检查复制或后续操作是否改变了内容。迁移另有文件级清单。

本步待确认：第一版是否只使用这两批来源。新增来源时应保存为新的批次，不能直接混进旧文件后仍沿用旧版本名。

天气和家居统一采用修订后的最新评分版本，不再比较或选择旧规则。当前天气为 283 条通过、17 条未通过；家居为 288 条通过、11 条未通过。对应文件均为各场景 `data/raw` 目录中的 `scores.current.json`。统一提示词和工具说明同步采用这些规则，例如天气城市名允许省略末尾的“市”。

## 6 步骤三 确认统一模型输入

### 目前的草稿是什么

`system-prompt.txt` 把天气助手和家居助手合成一个中文智能助手，分三部分说明行为：共同规则、天气规则、家居规则。每条样本再追加当次日期、时区，以及家居场景中原来可见的设备目录。

例如共同规则要求不编造工具结果；天气规则说明缺城市时怎样处理；家居规则说明什么情况下能控制、什么时候要回读，以及结果不确定时怎样回答。具体工具参数单独放在 `tools` 中。

当前候选为每条数据同时提供三个工具：`get_weather`、`state_hub_snapshot`、`hass_set_state`。这与原来的单场景生成环境不同，所以需要重新检查模型在多个工具都可见时是否仍能正确选择。

### 哪些内容可以进入输入

| 内容 | 是否进入模型输入 | 理由 |
|---|---|---|
| 用户已经说过的话 | 是 | 模型必须理解当前需求和历史 |
| 当前可用工具的定义 | 是 | 模型必须知道能调用什么、参数怎么写 |
| 已经返回的工具结果 | 是 | 它是后续决策的依据 |
| 当次可信设备目录与权限 | 是，前提是应用实际提供 | 模型不能凭训练记住某个设备是否可控 |
| 当前日期与时区 | 由应用提供 | 相对日期需要明确基准 |
| 种子中的最终目标或评分答案 | 否 | 这是评分信息，会泄漏答案 |
| 未来的用户回复 | 否 | 模型当时不可能提前知道 |
| 模拟器隐藏状态、未来故障计划 | 否 | 应通过实际工具返回逐步获知 |

日期与时区是从会话元数据加入新输入的，并不代表原模型当时已经看到过这些字段。设备目录不带初始状态，状态仍通过工具取得。

### 还需要确认什么

统一身份、输出风格、工具开放范围，以及最终推理时由哪一层提供动态上下文。天气和家居的评分规则已确定采用最新修订版，不再重复确认。训练项目维护这份输入约定，将来的调用端按约定传入内容；不在本阶段修改 server 的线上提示词。

训练集里的第一条 system 被改写后，旧轨迹不会自动获得新条件下的“合格证”。需要对重点样本复核，并在统一提示词与工具集下重跑独立案例。原 system 完整保存在原始数据中，随时可以回查。

## 7 步骤四 质量筛选和当前候选结果

### 筛选器已经做了什么

导出器检查对话是否完整、工具调用是否有对应返回、调用参数是否符合工具定义、用户轮次是否与原始记录一致、system 校验值是否一致、家居目录是否与原本可见的目录一致，以及评分是否齐全。

通过检查后，调用参数从 JSON 字符串转换为对象；随机调用 ID 按顺序规范化，同时更新工具返回的关联 ID。用户、助手、工具返回的正文保持原样，不补造结果，不把错误回答自动改写成正确答案。

### 当前导出的实际数量

以下统计已按最新修订评分重新整理：

| 去向 | 天气 | 家居 | 合计 |
|---|---:|---:|---:|
| 训练候选 | 225 | 222 | 447 |
| 测试候选 | 58 | 51 | 109 |
| 未通过样本，训练侧 | 15 | 8 | 23 |
| 未通过样本，测试侧 | 2 | 3 | 5 |
| 待复核轨迹 | 0 | 15 | 15 |
| 总数 | 300 | 299 | 599 |

当前通过筛选并导出的候选共 556 条，未通过样本 28 条，待复核 15 条。这里仍叫候选，因为目标模型格式检查和统一提示词下的行为复核尚未完成。测试侧的任何样本都不用于更新模型。

评分通过与结构合格是两个条件：家居虽然有 288 条评分通过，但其中 15 条依赖运行器插入的提示，先放入待复核，因此实际导出 273 条。

### 15 条为什么没有进入 SFT

它们包含运行器插入的“已达到最大工具调用次数，请直接给最终答案”提示。助手的后续回答可能依赖这条提示。

如果把提示删掉，后续回答的输入条件就变了；如果把它当普通用户说的话，又会教出错误的对话结构。所以此版先整段隔离，保留原轨迹和原因。后续可以决定重生成、截取已验证的正确前缀，或显式设计运行器消息格式。隔离不等于永久丢弃。

### 未通过样本只做统一保存

28 条未通过样本保留原轨迹、失败项和评分证据，按已有划分存入 `failed.train.jsonl` 与 `failed.test.jsonl`。它们**可能可用于后续 DPO rejected**，但现在不判断适用性、不配对、不补 chosen，也不把它们命名为 DPO 数据。

“未通过”是模型行为在当前评分中不合格；“待复核”是输入结构或依赖关系需要先弄清楚。两类分别保存，避免把结构问题直接当成模型的错误行为。

### 已经验证到什么程度

导出器单元测试通过；599 条去向对账通过；训练与验证的模板、相同完整用户消息序列没有跨集合重叠；原始文件未改变；相同输入和代码可重复产生相同导出结果。

这些是程序和数据结构层面的检查。尚未逐条人工复核，也没有完成改写提示词后的行为评测。独立运行检查已通过；本次目录调整后也重新执行自检。

## 8 步骤五 划分训练和测试数据

当前输出统一使用 `train.jsonl` 和 `test.jsonl` 两个名称。train 用于训练；test 留出用于检查模型，不参与参数更新。

这批历史案例已经参与过开发，所以这里的 test 属于开发测试集，不冒充完全独立的最终测试。以后如果需要用一部分数据选训练轮次，再从训练侧按分组划出 validation；独立最终测试另行锁定，目前不再增加这些目录。

当前先对全部 599 条按模板分组，再筛选质量。相同场景与模板的所有改写放在同一侧；如果不同模板产生相同完整用户消息序列，也合并为同一组。这比将每条对话随机打散更能减少相似问题同时出现在训练和验证中。

划分时目标约 20% 测试，但以整组为单位，所以筛选后的比例不要求恰好 80 比 20。由同一案例派生的修正版和截取片段，也必须沿用原来的划分。

当前 109 条测试候选保留上述开发测试定位。相同语义但表达不同的跨模板近似案例，还需要进一步查重。

本步完成标志：确认分组划分规则，锁定测试范围，后续修订或拆分的样本仍继承原分组。用于反复调参的数据不能继续称为独立最终测试。

## 9 步骤六 检查是否需要补充数据

现在的数据主要按天气、家居分别生成。需要检查它们是否覆盖跨场景切换、同轮多个请求、普通闲聊和无需调用工具等情况。例如“查一下北京今天的天气，再打开客厅灯”，要求模型完成两类任务；“别开灯，我只想安静坐一会儿”，则不应触发控制。

之前整理过 10 个补充任务建议，现放在 `archive/before-simplification/plans/supplemental-cases.draft.json` 备查。它们只是任务输入，不是已经生成的训练数据。

本项目负责发现缺口、验收补充数据，不在这里重写对话生成器。需要补数时由原生成流程提供带工具交互的完整轨迹，再按同一套规则评分、划分和导入。现在不把这一步展开成独立的生成项目。

## 10 步骤七 验证 Qwen3.5 9B 的数据格式

这一阶段还未开始实际适配。上轮只在本机临时目录安装过 Python tokenizer 相关依赖，没有下载模型权重，没有完成 tokenizer 下载或标签验证。那个临时环境不作为训练服务器环境，也不随本项目迁移。

### 首先锁定准确的模型版本

Qwen3.5-9B 是用户已确认的型号，但仍要记录准确模型仓库、revision、tokenizer 和配置文件。不能直接套用 Qwen3-8B 的模板、依赖版本或训练脚本。是否使用量化版本、是否关闭思考模式，也要在此阶段确认。

### 模型到底要学习哪些内容

训练时每段文字都会被切成 token，也就是模型处理的小单元。“只对 assistant 计算损失”指只要求模型学习助手应该生成的回复和工具调用；system、用户消息和工具返回都作为上下文，不作为助手的生成目标。

举例：

```text
用户：打开客厅灯                 作为输入，不作为答案学习
助手：调用状态工具               学习这一决策和调用参数
工具：客厅灯当前关闭             作为输入，不让助手学着伪造它
助手：调用开启工具               学习这一决策和调用参数
工具：请求已接受                 作为输入
助手：回读状态                   学习核验动作
工具：客厅灯当前开启             作为输入
助手：客厅灯已经打开了           学习有依据的最终回复
```

JSONL 中保存 `role` 并不会自动实现这种屏蔽。必须检查真正送进训练器的 token labels，确认工具返回没有意外参与损失计算。也要确认工具调用没有被过滤掉，否则模型只学会说话而没有学会执行。

### 测长度后再定训练参数

用目标 tokenizer 统计整条对话的真实 token 长度，至少记录中位数、高分位和最长样本。不能只看汉字数量，也不能先设一个较短上限，把长工具链截掉后直接训练。

过长样本应明确选择增加上下文、按完整决策边界拆分，或暂时移出。拆分后的片段必须保留足够历史，并继承原样本的数据划分。

本步完成标志：工具模板渲染正确、参数格式正确、长度分布有报告、角色屏蔽有实际样例、训练与推理使用一致的模板及思考模式。

## 11 步骤八 冻结第一版训练包

冻结的意思是：这一版要用的内容确定下来，不在训练过程中悄悄改文件。

第一版训练包应包括已确认的 system 和 tools、训练与验证数据、逐条来源清单、筛选规则、划分规则、精确模型和 tokenizer 版本，以及全部重要文件的校验值。还要列清楚哪些场景覆盖了，哪些没有覆盖。

当前结果放在 `data/prepared`，仍然是候选，不是冻结后的正式训练包。改版前的结果已归档；每次正式改版都保留旧清单，不覆盖已经用于训练的版本。

本步完成后再复制到训练服务器。新增修正应形成 v1、v2 等新版本，而不是覆盖已经训练过的版本。

## 12 步骤九 训练服务器环境与小规模试跑

该阶段在用户的训练服务器执行。先记录操作系统、GPU 实际可用显存、驱动、CUDA、Python、PyTorch、Unsloth 和相关训练依赖版本。

硬件按用户确认的单卡 32GB 规划，但不能只凭显存容量承诺任意上下文和 batch 都能跑。模型加载方式、优化器、序列长度和 DPO 的两个候选都会影响实际用量。

先跑很小的一批数据，检查模型能否加载、loss 是否正常、训练能否保存并恢复、保存后的模型是否能生成有效工具调用。再根据实际显存峰值确定 batch、梯度累积和上下文长度。

几个常见参数用普通话解释：batch 是一次处理多少条；梯度累积是分几次处理后再更新一次参数；LoRA 是只训练一小部分新增参数；QLoRA 是在量化底座上训练 LoRA，用来降低显存需求。是否采用这些方案和具体数值，等待本阶段确认，不在文档里预填成已经验证的配置。

本步完成标志：环境可复现，小批次能够完整训练、保存和推理，且没有混入验证数据。

## 13 步骤十 SFT 训练和第一次模型评测

SFT 使用已验收的正确示范，让模型学习什么时候澄清、怎样选择工具、怎样填写参数、怎样根据返回继续任务，以及如何如实报告结果。

正式训练前，先让原模型在固定评测集上跑一遍，留下基线。然后训练 SFT 模型，在相同提示词、相同工具集和可复现环境下再测一次。这样才能知道改进来自训练，而不是换了提示词或工具行为。

评测不只看文字是否顺口，至少关注任务完成率、工具选择和参数、重复控制、无依据的成功声明、该澄清时是否澄清，以及信息齐全时是否过度追问。普通聊天、无需工具、跨场景组合也要检查。

验证 loss 可以作为训练过程信号，但不能替代任务评测。模型可能很会模仿回复格式，却没有正确执行工具链。

本步交付：SFT 模型或适配器、完整配置、训练日志、可复现加载方式，以及与原模型的对比报告。如果 SFT 本身还没有学会基本流程，先修正数据与训练，不急着用 DPO 掩盖问题。

## 15 步骤十二 最终对比和交付

最后在相同条件下比较原模型、SFT 模型和 SFT 加 DPO 模型。只有 DPO 确实改善了目标行为且没有明显损害其他能力，才选择它作为最终版本。

重点检查“更少犯错”和“仍然能完成任务”是否同时成立。例如不能用任务拒绝率大幅上升，换来表面上更少的工具错误；也不能因为回复更简短，就忽略遗漏的用户需求。

最终交付应包括模型或 LoRA 适配器、准确底座版本、tokenizer 和推理模板、system 与 tools 输入约定、训练数据版本和配置、评测报告、失败案例，以及训练服务器上的加载示例。需要合并或量化时，另做导出后回归检查。
