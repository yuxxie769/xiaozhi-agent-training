### 4.2 程序盘点只统计三项

| 维度 | 统计内容 |
|---|---|
| 来源与数量 | 每个来源文件作为一批，记录场景、数量和原有 run_id |
| 任务覆盖 | template_id、variable_group_id、question_pattern_id、variant_id、scenario_ids 的已有取值及样本数 |
| 对话结构 | 单轮、多轮数量，以及消息数、正文字符数、工具调用次数、单次调用参数字符数的分布 |

盘点面向全部 599 条轨迹，包括未通过、待复核和重复项。任务标签直接读取 seed，缺失记录为“未提供”，不推断新标签。一个样本可包含多个场景标签，因此标签数量不能相加作为总样本数。

轮数按真实 user 消息计算，排除 internal_message_indices 标记的运行器提示。消息数和正文字符数统计原始完整轨迹，包含 system 和运行器消息；正文不包含工具调用参数。参数字符串按原文计数，对象按紧凑 JSON 计数。这些都是字符数，不是模型 token 数。

分布提供最小值、中位数、P90 和最大值；P90 使用最近秩法，即升序第 ceil(0.9×数量) 项。无观测值时统计值为 null，不伪装成零。

当前天气有 165 条单轮、135 条两轮；家居有 87 条单轮、197 条两轮、15 条三轮。具体模板、变量组和标签计数见 `inventory.json`，摘要见 `report.md`。本流程不生成覆盖不足分析或补数建议。

### 4.3 每条训练输入如何构成

| 部分 | 做法 |
|---|---|
| system 固定规则 | 使用根目录 system-prompt.txt，涵盖共同规则、天气规则和家居规则 |
| system 设备目录 | 从该条原始 system 提取并原文保留可见目录块，包括字段、设备及别名顺序 |
| messages 后续消息 | 保留用户消息、助手回复及调用、工具返回，不改正文 |
| tools | 每条样本携带相同的 9 个非 MCP 工具定义，与 messages 并列 |

完整工具列表保存在根目录 `tools.json`：get_weather、get_news_from_newsnow、play_music、get_lunar、handle_exit_intent、hass_get_state、hass_set_state、state_hub_snapshot、task_engine_control。天气和家居样本都提供这 9 个工具，不按场景缩小范围。

列表按本批设备身份的当前管理端配置与本地开放规则提取，排除 MCP 及依赖 MCP 的包装工具；来源记录在 `tools-source.json`，不包含连接密钥。天气描述沿用已确认的最新评分规则，参数与当前 server 一致。原轨迹工具范围仅用于历史评分和追溯，不用于裁剪训练输入。

`messages` 与 `tools` 分开存储；训练适配时一起传给 Qwen3.5 聊天模板，由模板把工具定义放入模型输入，不手工拼接两遍。

日期、时区不从 context 元数据添加。原始用户消息、助手回复和工具返回中的日期正常保留。设备目录必须来自原始 system，并与元数据 public_catalog 对照；不一致或无法可靠提取则进入待复核。目录只提供身份与权限，不能代替工具返回的实时状态。

种子目标、评分答案、模拟器隐藏状态和未来故障计划都不进入训练输入。工具参数从 JSON 字符串转换为对象，随机调用 ID 按顺序规范化，并同步更新对应工具返回的 ID；这些处理不改变调用语义。

### 4.4 检查、分类与去重

导出器检查对话是否完整、消息顺序、工具调用与返回对应关系、参数格式、system 校验值、设备目录，以及评分对应关系、检查项和证据。

| 去向 | 天气 | 家居 | 合计 |
|---|---:|---:|---:|
| SFT 训练数据集 | 283 | 273 | 556 |
| 未通过样本 | 17 | 11 | 28 |
| 待复核 | 0 | 15 | 15 |
| 完全重复项 | 0 | 0 | 0 |
| 总数 | 300 | 299 | 599 |

训练集只接收评分通过且结构与输入检查通过的轨迹。完全相同的规范化 messages 和 tools 才算重复；只保留一条，并记录其他原始样本对应的保留项，不做语义近似去重。

未通过样本保留失败项、证据和错误调用，不自动修成正确答案；对格式可解析的错误工具名或参数，记录 invalid_actions，并标明它针对原生成工具范围。目标工具列表中的合法性另记为 target_invalid_actions；新增工具不会让旧失败自动变成通过。结构本身无法可靠还原的样本进入待复核。

15 条待复核轨迹包含运行器插入的工具调用限次提示。删掉这条提示会改变后续回答的输入条件，因此本次整段保留在 raw，记录来源和原因，不直接用于训练。待复核不代表永久丢弃。

## 6 当前阶段：验证 Qwen3.5-9B 训练适配

**直接使用现有 train.jsonl，不重新开展数据准备。** 模型已锁定为官方指令模型 `Qwen/Qwen3.5-9B`，revision 为 `c202236235762e1c871ad0ccb60c8ee5ba337b9a`。不使用 `Qwen/Qwen3.5-9B-Base`，因为当前数据是在已有对话和工具能力上继续监督微调。

Qwen3.5-9B 在 Transformers 中的架构是 `Qwen3_5ForConditionalGeneration`。它带有视觉组件，即使本项目当前只训练文本，也不能把它当成普通的旧版纯文本 Qwen 类直接套脚本。训练适配应通过模型的 Processor 和官方聊天模板处理消息与工具；Unsloth 侧按 Qwen3.5 的多模态架构加载，文本数据不提供图片输入，也不训练视觉层。

当前统一采用非思考模式。训练模板与后续基线、SFT、DPO 评测都传入 `enable_thinking=False`，避免训练输入和上线推理格式不一致。Qwen3.5 不使用 Qwen3 的 `/no_think` 文本指令切换方式。

已加入 `scripts/validate_qwen35_adapter.py`。它只下载 Processor/tokenizer，不加载约 19GB 的模型权重，也不会启动训练。脚本会对全部 556 条样本执行：

1. 将每条 `messages` 和对应 `tools` 一起交给目标聊天模板，确认 9 个工具进入模型输入，工具调用和工具返回都能渲染。
2. 使用 TRL 的训练模板补丁生成 assistant mask，并用独立哨兵样本确认只有 assistant 正文和工具调用参与损失；system、工具定义、user 和工具返回全部作为上下文屏蔽。
3. 使用实际 tokenizer 统计完整输入 token 长度及 assistant 监督 token 长度，报告超过 2048、4096、8192、16384 和 32768 的样本数。这里不截断任何轨迹。
4. 在报告中记录模型 revision、Processor/tokenizer 类名以及 Python、Transformers、TRL 版本。

在训练服务器安装好 Unsloth 及其匹配依赖后运行：

```bash
cd /path/to/xiaozhi-agent-training
python3 scripts/validate_qwen35_adapter.py \
  --dataset data/prepared/train.jsonl \
  --output data/adapter-validation/qwen35-9b-c202236.json
```

输出路径必须不存在，脚本拒绝覆盖旧报告。预检通过之前不写正式训练参数；上下文长度、batch、LoRA/QLoRA 和显存方案均以这份报告及单卡 32GB 的实测结果为准。

训练适配的完成标志仍是：556 条全部渲染成功，工具调用可还原，assistant-only 掩码通过哨兵检查，长度统计完整，并且训练和推理采用同一模型 revision、工具列表、聊天模板与思考模式。

## 8 SFT、模型评测与后续 DPO

正式 SFT 前，在固定的新评估种子上运行原模型作为基线。训练后使用相同提示词、工具条件和评分规则评测 SFT 模型，比较任务完成、工具选择与参数、重复控制、无依据的成功声明及澄清行为。测试种子不进入训练集。

本阶段没有留出验证集，训练脚本不能默认寻找 test.jsonl。后续如需独立验证 loss，应另行确定验证数据来源；不在当前流程中暗自划分。训练 loss 本身也不能替代任务评测。

SFT 交付模型或适配器、配置、训练日志、加载方式和基线对比。之后再根据实际错误展开 DPO 方案，现存 failed.jsonl 不直接等于 DPO 数据集，也不保证每条失败都能作为 rejected。

最后在相同条件下比较原模型、SFT 和 SFT+DPO，交付选定模型、准确底座及 tokenizer、输入约定、训练配置、评测报告和加载示例。接回 agent server 属于后续集成，不在本项目修改原 server 的部署。
